# Local subaccount creation helper

User verification: HOT Wallet blocked the `Add full key` action in the creation transaction. The helper now refuses this known HOT path before opening another signing request and explains the limitation. Use another signer for the same parent account or NEAR CLI; this helper must not be described as a working HOT creation flow. Read-only mainnet check after the block found `tor.nuvelorian.near` absent. Keep the generated child backup/key for any subsequent creation attempt.

Run `npm run start:market` and open `http://127.0.0.1:4183/near-subaccount` in a regular browser with HOT available. This page exists only in development builds and has not been deployed. No on-chain transaction has been executed by the assistant.

Connect the actual parent mainnet account. The page derives the child from the connected account, never from the game's configured payment receiver. Select `tor` or `grym`. Generate a fresh Ed25519 child key locally, set a separate backup password (12+ characters), download the encrypted backup, and keep password and file separately. The page never requests the parent seed/private key. Child private keys stay in memory and in the AES-GCM encrypted download; no plaintext key is sent to the server, stored in browser storage or logged. PBKDF2-SHA256 uses 600,000 iterations and a random salt. Restore uses the same page's backup file picker and password field, entirely locally. It reconstructs the existing child key rather than generating another.

The explicit wallet button asks the user to approve a mainnet transaction: `CreateAccount`, transfer exactly 0.1 NEAR, add the child key with `FullAccess`. The signer is the connected parent, receiver is its immediate child. No parent keys or contracts are modified. Wallet support for these action types must still be validated with the user's HOT client; a successful live signing is not claimed. No FT registration, PL4 transfer or market agent signing is enabled by this helper.

After a signing attempt, uncertain outcomes disable sending again. Verify the account and exact full-access public key without another payment. A timeout/RPC error never counts as account absence. After a known wallet rejection, supported rejection codes allow retry; for other errors keep the backup and reconcile the original attempt before retrying. The server exposes only fixed mainnet read queries through a loopback-only endpoint; it cannot sign or broadcast.

Browser automation is unavailable in the current desktop environment; page module compilation and service/crypto tests are used. Do not claim visual or live-wallet verification.

The explicit “Download NEAR file with private key” button exports standard plaintext `{account_id, public_key, private_key}` JSON locally. The `private_key` field is the Ed25519 key for wallets supporting private-key import. This user-requested export is not encrypted; it is never sent to the server. No mnemonic is generated. The private key remains in memory after creation so export still works; after reload recover the original encrypted backup with its password. Import requires the account to have been created on-chain first. Restoring a backup does not create an account or replace its key. A user who has not signed (or definitively rejected) the original transaction may explicitly resume creation after a fresh account-absence check; unknown transaction outcomes must be reconciled first.
